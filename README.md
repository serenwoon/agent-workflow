# 문서 작업을 에이전트로 돌리는 법

장문 문서를 읽고 · 구조화하고 · 근거를 대조하는 일을 LLM 에이전트로 처리할 때, **틀린 결과가 조용히 통과하지 않도록** 만든 작업 구조다.

프롬프트 모음이 아니다. **판정 루프**다.

> 이 문서의 규칙은 전부 실제로 무언가를 틀린 뒤에 생겼다. 4절이 그 목록이다.

---

## 0. 출발점 — 문서 작업에는 컴파일러가 없다

코딩 에이전트가 잘 도는 이유는 **판정자가 있어서**다. 틀리면 컴파일러가 빨간 줄을 긋고, 테스트가 실패하고, 그 신호로 루프가 수렴한다.

문서 작업에는 그게 없다. 그래서 대부분의 "문서 AI"는 **그럴듯한 산출물을 빠르게 뽑고 거기서 멈춘다.** 틀렸다고 말해주는 게 없으니까. 남는 건 매끄럽지만 아무도 검증하지 않은 문서 더미다.

**이 구조의 전부는 판정자를 만들어 넣은 것이다.**

```
        ┌──────────────────────────────┐
        │                              │
        ▼                              │
   산출물 수정 ────→ 판정자가 검사 ─────┘
                        │
                   불일치 · 근거 없음 · 반론
```

---

## 1. 상태는 대화가 아니라 파일에 둔다

대화가 길어지면 초반 지시가 희석된다. 그래서 **매번 새 대화창을 열고, 상태는 폴더에 둔다.**

| 폴더 | 무엇 | 컨텍스트에 넣는 법 |
|---|---|---|
| `00_고정/` | 판정 기준 · 금지 목록 · 제약 | **매 호출마다 전부** |
| `10_원자료/` | 원본 문서 (읽기 전용) | 관련될 때 **원문 그대로** |
| `20_산출물/` | 실제 결과물 | 그 호출에 관련된 것만 |
| `30_역할/` | 판정자 프롬프트 | **하나씩. 절대 섞지 않는다** |
| `06_결정사항/` | `DECISIONS.md` (append-only) · `OPEN_ISSUES.md` | 판단이 갈릴 때 |

프로젝트 루트에는 `CLAUDE.md`(또는 동등한 프로젝트 지침 파일)를 둔다. → [`templates/CLAUDE.md`](templates/CLAUDE.md)

**돌리는 법**

```
① 00_고정 전부 + 관련 산출물 + 역할 하나  →  호출
② 나온 지적을 산출물에 반영
③ 버린 것과 이유를 금지 목록에 추가
④ ①로
```

## 2. 한 호출 = 한 역할

> "장단점을 균형 있게 평가해줘"라고 하면 **무난한 평균**이 나온다.
> **날을 세우려면 한쪽만 시켜야 한다. 균형은 사람이 잡는다.**

모델에게 균형까지 맡기면 아무것도 안 걸러진다. 확산과 수렴을 반드시 분리한다.

| 역할 | 언제 | 무엇을 잡나 |
|---|---|---|
| [질문 생성](prompts/01_question-generation.md) | 시작할 때, 막혔을 때 | **우리가 모르는 것.** 답보다 질문이 값질 때가 있다 |
| [회의론자](prompts/02_skeptic.md) | 방향을 정하기 **전** | 반대 논거만. 장점은 한 줄도 쓰지 않게 한다 |
| [일관성 검사](prompts/03_consistency.md) | 산출물 2개 이상 고칠 때마다 | 문서 **사이의 모순** |
| [근거 대조 검증자](prompts/04_evidence-audit.md) | 근거·수치가 많이 들어간 직후 | 인용이 원문을 실제로 뒷받침하는가 |

### 일관성 검사가 자동화 효율이 가장 높다

다른 역할은 판단이 섞이지만 이건 **기계적 대조**에 가깝다. 결과가 안정적이고, 사람이 잡기 어려운 걸 잡는다.
문서를 조금씩 고치다 보면 **A를 전제로 쓴 문서와 B를 전제로 쓴 문서**가 공존하게 된다. 안에 있는 사람은 못 느끼고, 밖에서 보는 사람은 5분 만에 본다.

### 검증자는 같은 세션에 두지 않는다

근거 대조는 **새 세션에서, 원본 문서만 들고** 시작한다. 내가 쓴 정리 노트는 주지 않는다.
같은 대화 안에서의 자체 검증은 약하다 — 자기가 만든 전제를 그대로 물려받기 때문이다.

## 3. 근거 규율

### 3-1. 근거 사다리 — 위에서부터. 건너뛰지 않는다

| 순위 | 어디 | 무엇의 근거인가 |
|---|---|---|
| 1 | **원본 문서** (`10_원자료/`) | 그 일의 모든 사실 |
| 2 | **조직 공식 자료** | 내부 용어 · 방법론 · 실적 |
| 3 | 용어집 | 용어 판정 기준 |
| 4 | 지식 노트 | 일반 개념 |
| 5 | 외부 검색 | **위 넷에 없을 때만.** `(외부 검색)` 표시 필수 |

**1·2를 확인하지 않고 5로 내려가지 않는다.** 내부 용어를 외부 검색으로 정의하면 **그럴듯한 오답**이 나오고, 그게 제일 위험하다. 모르면 검색하지 말고 **사람에게 묻는다.**

### 3-2. 확신 표시를 반드시 남긴다

| 표기 | 언제 |
|---|---|
| (표기 없음) | 원문·공식 자료로 확인됨 |
| `[확인필요]` | 원문 대조 안 함. **단정 금지** |
| `(외부 검색)` | 5순위에서 가져옴 |
| `[추정]` | 내 판단. 사실처럼 쓰지 않음 |

### 3-3. 링크가 아니라 구절을 옮겨 적는다

수치·조항·규격을 인용할 때 **링크만 다는 것으로는 부족하다.**
실존하는 문서를 링크하면서 그 문서가 뒷받침하지 않는 내용을 쓰는 일이 가능하고, **이건 파일명 기반 검사(grep)를 100% 통과한다.**

```
나쁨:  이 조문은 1년까지 운전을 금지할 수 있게 한다 (원문 링크)
좋음:  제97조① — "1년을 넘지 아니하는 범위에서 국제운전면허증에 의한
                  자동차등의 운전을 금지할 수 있다"
```

> 예시는 [extraction-benchmark](https://github.com/serenwoon/extraction-benchmark)에서 쓴 공개 법령 문서다.

### 3-4. 정의는 한 곳에만 둔다

같은 숫자·정의가 두 파일에 있으면 **그건 이미 사고 예비 상태다.** 원천 한 곳 + 나머지는 링크.
아래 4절 사고 ①의 수정 비용이 컸던 이유가 정확히 이것이다 — 틀린 정의가 이미 9개 파일에 복사돼 있었다.

## 4. 실패에서 나온 규칙 — 이 문서의 본체

각 줄은 **실제로 무언가를 틀린 사건**이고, 오른쪽이 그 결과로 생긴 규칙이다.

| # | 무슨 일이 있었나 | 그래서 생긴 규칙 |
|---|---|---|
| 1 | 내부 고유 용어를 **원본을 안 보고 외부 검색으로 정의**했다. 그럴듯한 답이 나왔고 확신 표시도 안 붙였다. 그 정의가 **9개 파일로 복사**됐고 발표까지 나갔다. 실제 정의는 **공식 자료 2쪽 각주 한 줄**에 있었다 | **근거 사다리**(3-1). 원인은 지식 부족이 아니라 **순서**였다 — 밖을 먼저 봤다 |
| 2 | 문서 변환기가 표 셀 안의 이스케이프 문자에서 셀을 잘랐다. 한 항목이 **5,270자 → 84자**로 잘렸고 전체로 **약 38,000자**가 사라졌다. 그런데 그 파일은 머리에 **"원문 전문"** 이라고 선언하고 있었다. 링크도 ID도 멀쩡했다 — **분량이 맞는지는 아무도 안 봤다** | 기계 추출물을 "전문"이라 부르기 전에 **원문에서 구절 몇 개를 실제로 옮겨 대조**한다. 특히 표·규격이 든 항목은 반드시 |
| 3 | 항목 본문(`□`)만 읽고 **단서(`※`)를 흘렸다.** 단서가 본문을 정면으로 부정하고 있었고, 결론이 **정반대**로 나갔다. 실측해보니 단서 136줄 중 **24개가 본문을 뒤집거나 한정**하고 있었다 | 인용·요약할 때 **본문·하위·단서의 개수를 세어 맞춘다.** 단서가 본문을 뒤집으면 **단서 쪽이 진짜 요구**다 |
| 4 | `연계정보`로 검색해 **0건** → "원문에 정의 없음"으로 단정. 실제 표기는 **`연계 정보`(띄어쓰기)** 였고 3건 있었다. 다른 용어는 **도면 이미지 안**에 있어 텍스트 검색이 닿지 않았다 | **"검색 0건"은 "없다"가 아니다.** 띄어쓰기 변형·단어경계·이미지·원본 포맷까지 네 단계를 다 거친 뒤에만 "없음"이라고 쓴다 |
| 5 | 추출 결과의 빈 표를 보고 **"그림이 소실됐다"고 단정**해 노트 3곳에 적었다. 그림은 파일 안에 온전히 있었다. **2일간 없는 것으로 취급**했고, 사람이 "혹시 못 보고 있는 거냐"고 묻고서야 확인했다 | 추출 결과가 비어 있으면 "없다"가 아니라 **"내 도구가 못 꺼냈다"를 먼저 의심**한다. 빈 셀·0바이트는 결론이 아니라 **확인 시작점**이다 |
| 6 | 문서 수를 집계하는데 **작업 사본 디렉터리가 같이 잡혀** 실제의 **4배**로 부풀었다. 그 숫자가 프로젝트 지침 문서에 박혔다 — **그 문서가 스스로 "사본을 제외하라"고 경고하고 있었는데도** | 집계 명령에 **제외 경로가 들어갔는지 눈으로 확인**한다. 규칙을 쓰는 것과 지키는 것은 다르다 |
| 7 | 정규식으로 항목 ID를 세어 **문서 제목보다 3개 많게** 나왔다. 데이터 오류로 의심했는데, **다른 문서의 ID를 참조한 3건**이었다. 원본에는 총계표가 있었다 | **정규식 집계는 문맥을 모른다.** 원본에 합계가 있으면 그게 정답이다. 도구 출력과 원본이 다르면 **도구를 먼저 의심**한다 |
| 8 | 파일 동기화 훅이 의존하는 CLI 도구가 설치돼 있지 않아 **매번 실패**하고 있었다. 게다가 경로 판정이 문자열 포함 검사라 **관계없는 편집에도 발동**했다 | **조용히 실패하는 자동화가 가장 위험하다.** 실패를 반드시 소리 나게 만들고, 판정은 넓은 문자열 매칭이 아니라 **정확한 대상**으로 한다 |

### 이 표에서 읽히는 것

여덟 건 중 **다섯 건(1·2·4·5·7)이 같은 실패다** — **도구가 준 결과를 원본과 대조하지 않고 사실로 받았다.**

> **원본에 접근할 수 있는데 파생물을 근거로 삼는 것**이 이 작업에서 가장 자주 나는 사고다.
> 나머지 셋(3·6·8)은 **자기가 쓴 규칙을 자기가 안 지킨 것**이다.

그래서 이 구조의 핵심은 프롬프트가 아니라 **원본을 언제 다시 보게 만드느냐**에 있다.

## 5. 결정과 미결을 파일로 남긴다

| 파일 | 규칙 |
|---|---|
| `DECISIONS.md` | **append-only.** 결정은 지우지 않는다. 뒤집히면 새 항목을 추가하고 이전 항목에 취소선을 긋는다 |
| `OPEN_ISSUES.md` | 미결. 해소되면 `DECISIONS.md`로 옮기고 취소선 |
| 금지 목록 | **버린 아이디어와 이유.** 쌓아두지 않으면 다음 대화창에서 같은 걸 또 제안받는다 |

템플릿 → [`templates/`](templates/)

> 실제로 이 방식으로 굴린 프로젝트에서 **가장 자주 갱신된 두 파일이 결정 로그와 미결 목록**이었다(각 16회·13회).
> 산출물보다 **판단의 기록**을 더 자주 고쳤다는 뜻이고, 그게 이 구조가 실제로 작동한 증거다.

## 6. 평가에 대해 — 재보고 알게 된 것

같은 작업을 사람과 파이프라인으로 나눠 실측한 기록이 따로 있다 → **[extraction-benchmark](https://github.com/serenwoon/extraction-benchmark)**
(공개 법령 문서에서 항목을 뽑아 구조화 표로 만드는 작업, 표본 10건)

거기서 나온 것 중 이 구조에 반영된 세 가지:

1. **단발 실행의 결과는 그 자체로 믿을 수 없다.** 같은 입력·같은 프롬프트로 10건 중 **2건이 실행마다 다른 답**을 냈다. → 반복 실행 + 다수결을 기본으로 한다
2. **일치율은 난이도를 못 본다.** 사람이 가장 어려워한 항목이 **채점에서는 만점**으로 잡혔다(사람과 기계가 우연히 같은 답을 골라서). → 골든셋에 **확신도(`확실`/`애매`)를 같이 받고, 채점을 확신도별로 나눠 본다**
3. **판정 기준의 결함은 불일치로 드러난다.** 일관된 불일치 2건을 파고드니 어느 쪽의 오류도 아니라 **내가 쓴 규칙이 그 경우를 못 가르는 것**이었다. → 불일치는 오답 목록이 아니라 **규칙 개정 목록**으로 읽는다

> 점수가 올라가는 걸 목표로 삼지 않는다. **판정자에게 과적합**된다.

---

## 7. 이식하는 법 — 새 프로젝트에서 30분

1. 폴더 5개를 만든다 (`00_고정` `10_원자료` `20_산출물` `30_역할` `06_결정사항`)
2. [`templates/CLAUDE.md`](templates/CLAUDE.md)를 루트에 복사하고 **판단 기준 한 줄**을 채운다 — *"이 문장이 ○○에서 통하는가"*
3. `00_고정/`에 **금지 목록** 파일을 만든다. 처음엔 비어 있어도 된다
4. `prompts/`에서 **[일관성 검사](prompts/03_consistency.md)** 하나만 먼저 가져간다. 효과가 가장 확실하고 가장 기계적이다
5. `DECISIONS.md`에 첫 줄을 적는다 — 왜 이 프로젝트를 이렇게 시작했는지

나머지는 **틀리면서 는다.** 4절의 규칙 여덟 개도 전부 그렇게 생겼다.

> [!warning] 이 구조가 죽는 방식
> **도구 세팅에 한 주 쓰는 것**, 그리고 **폴더를 예쁘게 만드는 것.**
> 설치는 30분에 끝내고 바로 실제 문서로 넘어간다. 판정자를 한 번도 안 돌린 폴더는 그냥 폴더다.

```
  OPEN_ISSUES.md                미결 목록
```

## 범위

개인 작업 방식을 정리한 것이다. **특정 조직의 문서·데이터·업무 내용은 들어 있지 않다** — 구조와 규칙만 옮겼고, 사고 기록의 소재는 전부 일반화했다.
구체적인 실행 예시가 필요하면 [extraction-benchmark](https://github.com/serenwoon/extraction-benchmark)를 본다. 공개 법령 문서로 같은 워크플로를 처음부터 끝까지 돌린 기록이다.
